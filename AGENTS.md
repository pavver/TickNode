# AGENTS.md

Guidance for coding agents (Claude Code, Gemini / Antigravity, Codex, …) working in this repository. `CLAUDE.md` and `GEMINI.md` only import this file.

TickNode is a node-based visual programming system for automation. The goal is a Home Assistant add-on that replaces HA's built-in automations, while TickNode also runs standalone. Rust 2024 workspace. The concepts are described in `README.md` and `ARCHITECTURE.md`.

- The engine runs on the server (`ticknode-server`); the browser is only an editor (`ticknode-editor`, **Leptos** CSR). Plugins are WASM components (**wasmtime + WIT**, `wit/plugin.wit`). The editor↔server protocol is postcard; the types are shared through `ticknode-shared`. The graph is stored as JSON.
- **Integrations (Home Assistant included) are separate plugins, never part of the core or the server.** All third-party nodes run as WASM plugins with limited capabilities.

## Language rules

- Talk to the user in **Ukrainian**.
- Documentation (`*.md`) and code comments are in **English**.
- **Editor UI text** is localized with Mozilla Fluent (`en`, `uk`); never hard-code UI strings (see *Editor → Internationalization*).
- **Errors the user sees in the UI** (an answer to their action, a plugin settings error under the form, validation, the plugin state error, a stub node's explanation) must be translatable: they are a `ticknode_shared::UiMessage { key, args, fallback }` (Fluent key, string arguments, final English fallback), never a ready-made sentence. Engine errors map to `error-...` keys in the editor's `ui.ftl` (`EngineError::ui_message`); a plugin's own errors (`configure`) use keys from its translations. A message without a key (`UiMessage::plain`, `From<String>`) just shows the English text.
- **Definitions are English.** Titles, descriptions, help, pin names, type and setting texts in node/plugin code are English; they are the fallback. Other languages come only from Fluent resources (see *Translations*). Ukrainian words that the text parsers accept as input aliases (`ticknode_shared::text`, `condition`, keyboard shortcut letters) stay.
- **Logs are always English and are never translated**: the server log (`tracing`), node and plugin messages (`host::log`, `ServerMessage::Log`) and the editor console. This is deliberate: when a user reports a problem from any locale, their logs can be read without translation. Plugin authors must log in English; this includes `#[error(...)]` texts, `host::log`/`warn`/`error`, and `[UI]`/`[ERROR]` lines the editor writes to its console (plain English constants, no `t!`). Exceptions are server errors (`i18n::ui_text`) and the settings-copy confirmation (`settings-copied`): both answer a user action and are translated.

## Commands

```bash
cargo build
cargo test -p ticknode-core -p ticknode-shared -p ticknode-server
cargo test -p ticknode-core --test plugins delay_queue -- --nocapture   # a single test
cargo test -p ha-plugin                                                   # the HA plugin's own logic on the host target (no wasm needed)

# Engine benchmarks (Criterion; optionally uses target/wasm32-wasip2/debug/math_plugin.wasm).
cargo bench -p ticknode-core --bench engine

# Plugins are wasm32-wasip2 components. The integration tests (ticknode-core/tests/plugins.rs) load
# target/wasm32-wasip2/debug/*.wasm and are SKIPPED when the files are missing (TICKNODE_REQUIRE_PLUGINS=1 makes them fail)
cargo build --target wasm32-wasip2 -p delay-plugin -p string-plugin -p math-plugin -p http-weather-plugin -p test-plugin -p ha-plugin
# The server uses release builds copied to data/plugins/
cargo build --release --target wasm32-wasip2 -p math-plugin && cp target/wasm32-wasip2/release/math_plugin.wasm data/plugins/

# Local dev loop: rebuild plugins/editor/server and restart the server on .dev-data/ (reload the browser)
./dev.sh                 # or a subset: ./dev.sh editor server

# Server (env: TICKNODE_BIND=0.0.0.0:8099, TICKNODE_DATA_DIR=data, TICKNODE_WEB_DIR=ticknode-editor/dist; settings in data/settings.json fall back to TICKNODE_TICK_MS=100, TICKNODE_TICK_BUDGET=0, RUST_LOG)
cargo run -p ticknode-server

# Editor (Leptos CSR, trunk). Not in default-members: `cargo build` at the root does not build it
cd ticknode-editor && trunk build            # → dist/, served by the server
cd ticknode-editor && trunk serve            # dev on :8080, /ws is proxied to 127.0.0.1:8099
cd ticknode-editor && trunk build --release  # needs wasm-opt (trunk downloads it)
cargo test -p ticknode-editor --target x86_64-unknown-linux-gnu   # geometry and i18n tests (no browser)
```

- The `wasm-bindgen` version in `ticknode-editor/Cargo.toml` must match the wasm-bindgen-cli used by trunk.
- In the dev profile dependencies are built with `opt-level = 2`: unoptimized Cranelift compiles plugins tens of times slower.
- Never run the server against the real `data/` directory for experiments: it rewrites `data/sheets/` and `data/sheets.json`. Use a copy (`TICKNODE_DATA_DIR`).
- When the graph format or the protocol changes, update the types in `ticknode-shared` (shared by the server and the editor).

## Architecture

### Crates
- `ticknode-shared` — `lib.rs` re-exports every serialized type: `values.rs` (`DataValue`, `DataType`, `NumberValue`, value type names), `definitions.rs` (node/pin definitions, inline values and split pins), `graph.rs` (graph models and node IDs), `protocol.rs` (editor messages and traces), `manifest.rs` (`Capability`, `PluginManifest`), plugin settings (`plugin.rs`), plugin-defined types (`types.rs`: `TypeDefinition`, `TypeRegistry`), `variables.rs` (`VariableScope`, `VariableKey`, `Variable`, `VariableLookup`, `VariableChanges`, `VariableCommand`, limits & validation), `sheets.rs` (`SheetId`, `SheetInfo`, `SheetSummary`, limits & validation), and `ui_message.rs` (`UiMessage`, `Translations`, `fluent_slug`). `NodeOutput`, `MathOp` and `LogOp` remain in `lib.rs`. `condition.rs` holds the Match model and input helpers with `condition/{operators,parsing,evaluation,display,error}.rs` (operator tables, parsing, evaluation, text presentation and errors). Extracted tests live in `definitions/tests.rs` and `condition/tests.rs`.
- `ticknode-core` — `lib.rs` re-exports the public API: `node.rs` (`Node`, `NodeContext`), `error.rs` (`EngineError`), `registry.rs` (`NodeRegistry`), `variables.rs` (`VariableStore`), `engine.rs` (`TickEngine` state and construction with disabled nodes set `disabled: HashSet<NodeId>`, `set_disabled`, `is_disabled`, `set_node_sheet`) with `engine/{nodes,connections,persistence,execution}.rs` (node editing, connections, graph/snippet import/export, tick execution and data pull), `builtin.rs` and `builtin/` (built-in node families, including `builtin/variables/`), `host.rs` (`HostState`: tasks, HTTP, logs, changed variables), `plugin.rs` (plugin records and public re-exports) with `plugin/{bindings,host,runtime,options,node,outputs,convert,loading,lifecycle,catalog,emissions}.rs` (WIT bindings, host imports, instances, `OptionStore`, `WasmNode`, output validation, value/type conversion, loading, enable/disable/settings, editor catalog and tick emissions), `custom_types.rs` (named types, Make/Break nodes), `stub.rs` (stub nodes), `translations.rs` (Fluent resources: core `locales/{en,uk}.ftl`, validation and merging of plugin resources). Extracted unit tests live in `tests.rs`, `tests/variables.rs`, and `plugin/tests.rs`.
- `ticknode-server` — axum: `/ws` (WebSocket, postcard) plus the editor's static files. `actor.rs` runs the engine on its own OS thread (ticks and commands sequentially, no locks), with editor command handling in `actor/commands.rs` (plugin commands in `actor/plugin_commands.rs`, variable commands in `actor/variables.rs`), sheet operations and summaries in `actor/sheets.rs`, and tests in `actor/tests.rs`; `storage.rs` — manages scenario sheets (`data/sheets.json`, `data/sheets/<id>.json`, migration from legacy `graph.json`, and trash directory); `plugins.rs` — discovery of `data/plugins/*.wasm` and plugin state, with config persistence and environment overrides in `plugins/config.rs` and tests in `plugins/tests.rs`; `ws.rs` — an editor session tracking `open_sheet` and filtering events.
- `ticknode-editor` — the editor: `state.rs` (`Editor`, a `Copy` set of signals including `sheets` and `open_sheet`) with `state/{graph,messages}.rs` (graph queries, `apply(ServerMessage)`, and minimal sheet bootstrap), `i18n.rs` (Fluent bundles, locale and `t!`) with `i18n/{definitions,values}.rs` (server-provided definition labels, UI messages, value and condition presentation), `connection.rs` (WebSocket and reconnects), `canvas.rs` (canvas composition) with `canvas/{camera,interaction,node,pins,wires,selection,paste}.rs` (viewport, pointer gesture state, node view, pin controls, wires, selection bounds and paste preview) and `canvas/interaction/motion.rs` (gesture updates and completion), `panels.rs` (public re-exports) with `panels/{palette,resources,variables,inspector,execution,console,tooltip,formatting}.rs` (palette, resources, variables placeholder, inspectors, execution traces, console, help overlays and display helpers), `plugins_panel.rs` (plugin state, toggle, permissions, settings form), `resource_menu.rs` (action picker for dropped/clicked resources), `inline.rs` (input value fields) with `inline/properties.rs` (node property rows), `match_editor.rs` (Match state and body) with `match_editor/{inputs,cases}.rs` (input rows and case/condition rows), `picker.rs` (dynamic property field, filtering and placement) with `picker/popup.rs` (popup lifecycle and keyboard navigation), `ui.rs` (design-system components), `geometry.rs`. Extracted unit tests live in `{categories,geometry,i18n,inline,match_editor,panels/resources,picker,plugins_panel}/tests.rs`.
- `ticknode-plugin-sdk` — the plugin SDK (wit-bindgen): `lib.rs` keeps bindings and public re-exports; `plugin.rs` defines `Plugin` (with `types()` and `configure()`), `PluginNode` and setting helpers; `events.rs` defines HTTP/task/trigger/output and WebSocket/emission types; `values.rs` provides `StructValue`, `Inputs::field*` and `field*()`; `pins.rs` provides pin builders; `host.rs` provides `host::*`; `export.rs` implements `export_plugin!` and the WIT guest adapter, using conversions in `convert.rs`. `*-plugin` are plugins; `test-plugin` exists only for host tests, with its factory in `lib.rs` and probes in `{execution,settings,typed,websocket}.rs` (execution/isolation, settings/options, custom types and WebSockets).
- `ha-plugin` — the Home Assistant integration (plugin name `home_assistant`, nodes `ha/action` (action/target pickers and snapshotted typed field inputs), `ha/entity` (typed Value/Previous data and Changed pulses), `ha/condition_<kind>` gates for time, sun, zone and async template (In → Yes/No plus Result; shared live state cache and HA-rendered local UTC offset), and `ha/trigger_<platform>` for time, time_pattern, sun, zone, event, homeassistant, mqtt, webhook, calendar, tag, conversation and template; type `ha.state`). It drives the sans-IO `Session` of the external crate `ha-core-client` (git dependency, no `runtime` feature) from `Plugin::tick`: `hub.rs` holds shared state, with `hub/{connection,subscriptions,requests,templates,options,collection,env}.rs` handling the session/tick loop, watchers, one-shot requests, template conditions, option publishing, output mapping and the `Env` trait. Host calls and the clock are injected; `hub/tests.rs` runs the hub with a scripted fake Home Assistant on the host target. `actions.rs` re-exports service discovery, picker filtering/order and the snapshotted action node from `actions/{catalog,options,node}.rs`; `triggers.rs` keeps platform schemas and re-exports `triggers/{config,outputs,node}.rs` (typed configuration, output projection, node lifecycle); `conditions.rs` keeps gate schemas and re-exports `conditions/{evaluation,node}.rs`. `lib.rs` defines the plugin, `runtime.rs` adapts host calls/logging and shared hub access, `entity.rs` defines the entity event source with pure inference/conversion in `entity/value.rs`; `convert.rs` maps states/JSON to `DataValue`, `queue.rs` is the bounded FIFO queue. Extracted inline tests live in `tests.rs` and `{actions,entity,hub}/tests.rs`. The host test `ha_plugin_*` in `ticknode-core/tests/plugins.rs` runs it against a fake HA WebSocket server. Defaults to `ws://homeassistant.local:8123/api/websocket`; the add-on overrides it with the Supervisor endpoint `ws://supervisor/core/websocket` (`TICKNODE_PLUGIN_HOME_ASSISTANT_URL`); the token is a secret setting. Missing states clear their output pins; `ha/entity` clears Value/Previous when the selected type cannot represent the state.

### Nodes and the graph
- **Confirmed pins and frozen nodes.** `NodeModel.pins` stores the base pin signature (before split fields). Loading/reviving a node freezes it if a confirmed pin disappeared or changed direction/kind/data type, or an input became required. Names and optional additions do not freeze; legacy graphs without signatures record current pins. Frozen nodes do not execute, poll, receive task results/emissions or yield data until `confirm_pins`; user property/split/settings edits accept their new contract. Signatures survive stub transitions.
- **Detached connections.** Invalid saved/revived pin connections become `GraphModel.detached_connections`, preserving exec/data kind, both endpoints, the changed end (target preferred) and its old directional row. Confirmation keeps them; removing a node drops touching detached wires. Snippets include internal detached wires and remap their IDs on paste.
- A node is recreated from `type_name` + `properties()`; this is the only persistence/copy mechanism (`export_graph`, `load_graph`, `export_snippet`, `import_snippet`). Every configurable node implements `set_property` and `properties()` symmetrically.
- `NodeRegistry::register(creator)` takes the definition from an instance with default properties; definitions are not described separately.
- Pins may depend on properties (`math/expression` derives inputs from the formula's variables; `list/*`, `object/*` take the type from `element_type`/`field_type`). `set_node_property` removes connections that became invalid and returns them in `RemovedConnections`.
- `NodeOutput::Clear(PinId)` (WIT `clear`, SDK `Output::Clear`) removes a data output from the cache, invalidates pure results like a data write, and omits the cleared pin from traces. Skipping an output still keeps its previous value. A connected source without a value gives optional inputs no value and silently blocks required inputs.
- A data input has one source: `connect_data` replaces the previous connection. `connect_exec` validates pins too.
- An unconnected data input (number/string/bool/any, enum) can get a value right on the node: `ClientMessage::SetInputValue`, `TickEngine::set_input_value`. It is stored among the properties as `in:<pin id>` (`input_value_property`) but is not passed to the node: `pull_inputs` substitutes it while nothing is connected. Values that no longer fit after a pin change are removed in `set_node_property`. Works for plugins too.
- **Split struct pins.** `TickEngine::set_pin_split(node, pin, bool)` stores `split:<pin>` = `Bool(true)` alongside `in:*`; neither is passed to the node. `node_definition`/`NodeInstance` expose effective field pins. Output fields project the original cached/pulled struct; input fields assemble a tagged object, with non-optional fields required and optional missing fields omitted. Splitting removes original connections; recombining removes field connections and inline field values. Graphs, snippets and stubs preserve split settings. Protocol: `SetPinSplit { node, pin, split }` → disconnect events and `NodeUpdated`. Virtual ids are `0x8000_0000 | (original_pin << 8) | zero_based_field_index`; the range `0x8000_0000..=0xbfff_ffff` is reserved (native registration rejects it; plugin definitions discard reserved real pins with a warning). One level only: original ids ≤ `0x3f_ffff`, 1–256 fields; append fields to preserve ids. Nested struct fields can still connect to explicit Make/Break nodes. Struct pins sharing an id across directions split together; other pins with that id are unchanged. The editor uses the existing row height and socket positions, with indented field labels and split/recombine buttons; Match retains a name/type row above its split fields.
- **Plugin-defined data types.** `DataType::Named("ha.state")` refers to a `TypeDefinition` (`title`, `color` `#rrggbb`, `TypeKind::Struct { fields: FieldDefinition { name, title, description, data_type, optional } }` | `TypeKind::Enum { values }`). The name contains a dot (`is_type_name`) and is written as-is in text (`parse_data_type`/`data_type_name`, `*_type` properties, Match inputs). A struct value is `DataValue::Object` with `type_name: Some(..)` (`get_type()` → `Named`; `#[serde(default)]` without `skip_serializing_if`, since postcard is not self-describing); an enum value is a `DataValue::String` from the list (validated by `text::parse_value_in` / `input_value_fits`). The registry is `TickEngine::types` (`TypeRegistry`); a plugin adds its types atomically, and a name clash or an unknown type in a field or pin fails the plugin load. Exact pin compatibility goes through `TypeRegistry::compatible` (the free `types_compatible` knows only `Any`): `Named(a)→Named(a)`, `Named↔Any`, `Named(struct)→Object`, `Named(enum)→String`; never `Object→Named` or `String→Named` as exact matches. Connections also accept `TypeRegistry::convertible`: String ↔ Number/Bool/Time/DateTime/Duration/Color, Number ↔ Bool, and String → named enum (exact member value only). Lists convert element by element, with the whole conversion failing if any element fails. Structures are never implicitly unpacked. Compatible connections keep their existing behavior (including Any and enum → String); converting wires are dashed and show translated source/destination types. For every struct the engine adds pure nodes `type/make/<name>` (fields → value; pin 0 is the output, fields are 1..=N) and `type/break/<name>` (pin 0 is the input, fields 1..=N; a missing optional field has no value), category `Data` (`custom_types.rs`). **Add new struct fields only at the end**: pins are positional. In Match a struct behaves like an Object (`condition::ops_in`), an enum offers `=`/`≠`/`has value` with a drop-down of values. A plugin node may not put an object with a foreign or missing tag on a `Named` output: the host drops the value and logs an error.
- **Required inputs.** `PinDefinition::required` (`serde(default)`; WIT `pin.required`; SDK `data_in(..).required()`). An input is set when a source is connected or, for text types and enums, a value is set on the node (`in:<pin>`); struct/list inputs need a connection. A node with an unset required input does not run (a pure node yields no value, an active node's `execute` is not called) and logs an error once until the state changes. A connected source without a value is skipped silently. In Make the required inputs are the non-optional fields. The editor highlights such a pin and node as Error (`Editor::required_missing`).
- `match` is a decision combinator. Properties: `inputs`, a list of `"<pin>:<name>:<type>"` (type `any` = "auto"), and `cases`, a list of `"<pin>: a > 10 and b != \"on\""` (parsing, evaluation and display live in `ticknode_shared::condition`; `and` binds tighter than `or`). Operators depend on the left input's type (`ops_for`: comparisons for numbers/time/duration, `contains`/`starts_with`/`len_*` for strings and lists, `has_field` for objects, unary `is_true`, `is_empty`, `has_value`, …); the right side is a constant or another input, and a constant is coerced to the input's type (`text::coerce_to`: `"07:30"` → time). A graph without `inputs` is the old format: inputs are derived from the names in conditions (Any, pins 1.. alphabetically), but only during `create_node`; after `Node::restored` the inputs are explicit, both in a new and in a loaded node. Each case is an exec output with a stable pin number; Else is pin 0. There is no separate Branch node.
- **Tick durations.** `DataValue::Ticks(u64)` is the last value variant and shares `DataType::Duration` with wall-clock `Duration`. Text accepts `10t`, `10 tick(s)` and Ukrainian `такт`/`такти`/`тактів` (case-insensitive), and formats ticks as `10t`. Match compares ticks with ticks and time with time; all mixed ticks/time equality and ordering operators, including `!=`, return false because Match has no tick clock.
- **Delay inputs.** Built-in `sleep` has exec In (0), Duration Delay (1), exec Out (4); the old UseTicks/TickDuration pins are removed. Plugin Queue/Ignore/Reset Delay keep their pin IDs and take one Duration Delay input. Missing values wait one tick. `HostState::ticks_for_value` and SDK `host::delay_for` accept ticks or time, rounding time up; WIT still takes ticks. Clock is unchanged.
- **Adaptive nodes.** `NodeDefinition.adaptive` advertises native adaptation (`false` for plugin definitions; no WIT field). `Node::adapt_to(pin, type)` changes persisted properties; `TickEngine::adapt_node` follows the property edit path, reconciling caches, roles, signatures, inline values and connections. Constant adapts output 0 with `text::default_of` (Duration defaults to one second). `AddNodeConnected` adapts before connecting and emits the adapted `NodeAdded` in the same history entry.
- The text form of values (fields on nodes, conditions) is `ticknode_shared::text`: `parse_value(text, &DataType)` / `format_value`; time `HH:MM[:SS]`, date-time `YYYY-MM-DD HH:MM`, duration `90` / `1h 30m` / `500ms`, color `#rrggbb[aa]`.
- **Property schema.** `NodeDefinition.properties: Vec<PropertyDefinition { name, title, description, kind }>` (`ticknode-shared/src/property.rs`, `#[serde(default)]`; WIT `property-definition`; SDK `PropertyDefinition::select/dynamic/text`) describes some of a node's string properties; a property that is not described keeps the plain text row, and the stored properties/graph JSON are unchanged. `PropertyKind::Text` | `Select(Vec<(value, label)>)` (a drop-down; labels are translatable) | `Dynamic { source, plugin }` (a searchable picker; `plugin` is filled by the host with the owning plugin, plugins leave it empty). The host does not validate a `Select` value: the node's `set_property` does. The editor shows the translated title (`i18n::property_title`) and option labels (`property_option_label`); a described property is still one `ROW_H` row, so geometry is unchanged.
- **Dynamic options.** A plugin publishes `PropertyOption { value, label, detail, icon: Option<"mdi:name"> }` lists with the host function `set-options(source, options)` (SDK `host::set_options`), callable from any plugin call (`configure`, `plugin-tick`, `execute`); it replaces that source. Limits: 20 000 options per source, 256 sources per plugin (including entity domain lists and target-domain unions), 512 bytes per string (an over-long or empty-valued option is dropped, an English warning goes to the node log). The store (`OptionStore` in `plugin.rs`) lives in the plugin `Runtime`, so it survives a crash, and is cleared on disable. `TickEngine::property_options()` feeds `Init.property_options`; `take_property_option_changes()` returns only sources whose list changed (a disable reports them as empty lists), and the actor broadcasts `ServerMessage::PropertyOptions { plugin, source, options }` after every tick and every command. An empty list removes the source in the editor (`Editor::property_options`, keyed by `(plugin, source)`).
- **Property picker (editor).** `picker.rs`: `PickerField` is the field on the node (current value as icon + label, raw value if the list lacks it); clicking it sets `Editor::picker`, and `PickerLayer` (mounted at the app root, `position: fixed`, so it renders above the transformed canvas) shows the popup: search box (case-insensitive terms over label, detail and value), at most 100 rows (`MAX_ROWS`), up/down/Enter/Esc, Enter with no match (or the "Use ..." row) sets the typed text, `placement` opens it upwards near the bottom and clamps it on narrow screens. It sends `SetProperty` like other property editors and closes on a press outside, camera change or node removal. Icons are Material Design Icons (`@mdi/font`, bundled in `ticknode-editor/assets/mdi/`, license in `LICENSE-MDI.txt`; no CDN): `mdi:xyz` renders as `<span class="mdi mdi-xyz">`.
- Node positions belong to the server, not the engine; they are written into `NodeModel.position` only when saving.

### Translations (core and plugins)
- Texts of nodes, data types, categories and plugin settings are **Fluent resources shipped by the server side**, not by the editor. The core embeds `ticknode-core/locales/{en,uk}.ftl` (built-in nodes); a plugin ships `(locale, ftl)` pairs through the WIT export `translations` (SDK: `Plugin::TRANSLATIONS`, usually `include_str!("../locales/uk.ftl")`). The `en` resource is optional for plugins: the definition text is the English fallback. A core test requires en.ftl to equal the built-in definitions and both locales to have the same keys and a title/description/help for every built-in node.
- **Key conventions.** Fluent ids allow only `[a-zA-Z0-9_-]`, so names are slugified with `fluent_slug` (lowercase, every other character, including `/`, `.`, `_`, becomes `-`): nodes `node-<type slug>-title|description|help` and `node-<type slug>-pin-<pin>` (the pin name as written if it is `[A-Za-z0-9_-]`, otherwise its slug); described properties `node-<type slug>-prop-<name>-title|description` and `node-<type slug>-prop-<name>-option-<value slug>` (name written the same way as for pins); categories `category-<slug>`; data types `type-<name slug>-title|description|field-<field>|value-<value>`; settings `setting-<plugin slug>-<key slug>-title|description|option-<value>`; resource collection title `<plugin slug>-resource-<id slug>-title`, action title `<plugin slug>-resource-<id slug>-action-<type slug>`; free keys (plugin UI errors) `<plugin slug>-...`. Make/Break nodes are titled from the translated type (`custom-make-title` etc. in `ui.ftl`).
- **Validation (`translations.rs`, at `add_plugin`).** Every resource is parsed with `fluent-syntax`; a resource with syntax errors is rejected (English warning in the server log), locale codes are normalized (invalid ones ignored). Messages whose ids are outside the plugin's prefixes (`node-<own type slug>-title|description|help|pin-*|prop-*`, `type-<own type>-title|description|field-*|value-*`, `setting-<plugin>-*`, `category-*`, `<plugin slug>-*`; terms only `-<plugin slug>-*`) are dropped with a warning. `TickEngine::translations()` merges core first, then enabled plugins in name order; the first definition of an id wins (so category keys may collide without error, and nothing overrides the core).
- **Delivery.** `ServerMessage::Init { translations }` and `Catalog { translations }` (enable/disable changes the set) carry the merged `(locale, ftl)` pairs. The editor adds them to its bundles after `ui.ftl` (`i18n::set_runtime_translations`); lookup order: active locale, `en`, the definition's text. A plugin's UI error keys are restricted to its `<plugin slug>-` namespace (otherwise the key is dropped and only the fallback is shown).

### Home Assistant add-on (`ha-addon/`)
- `repository.yaml` (repo root) makes the repository addable in the HA add-on store; the add-on is `ha-addon/ticknode/` (`config.yaml`, `Dockerfile`, `run.sh`, `DOCS.md`, `README.md`, `CHANGELOG.md`). Ingress on port 8099 (HA strips the prefix and proxies WebSockets; the editor uses relative asset URLs and a relative `ws` URL, so no `X-Ingress-Path` handling), `homeassistant_api: true`, `init: false`, no exposed ports.
- HA builds repository add-ons with the add-on directory as the build context, so the Dockerfile's `source` stage clones `TICKNODE_REF` (default `master`) from GitHub. Locally/CI use the workspace: `docker build --build-context source=. -f ha-addon/ticknode/Dockerfile ha-addon/ticknode`. Trunk is pinned by `TRUNK_VERSION` and downloads the wasm-bindgen matching `Cargo.lock`.
- `image:` is deliberately omitted from `config.yaml` (commented) and `.github/workflows/addon.yml` has `push: false`: nothing is published to ghcr.io until release. Keep `version` in `config.yaml` in step with the workspace version.
- Bundled plugins live in the image at `/opt/ticknode/plugins` and are passed through `TICKNODE_BUNDLED_PLUGINS_DIR` (a generic server feature: scanned in addition to `<data>/plugins`, the user's same-named file wins; their config/data stay under the data dir). `run.sh` passes `SUPERVISOR_TOKEN` as `TICKNODE_PLUGIN_HOME_ASSISTANT_TOKEN`.

### Persistence
- Frames (`Frame`, `FrameId`, `FrameColor`) are layout rectangles saved in `GraphModel.frames` sorted by id, loaded into the actor and dropped if invalid. The engine ignores frames.
- Graph snapshots and JSON include confirmed `pins` and `detached_connections` (sorted by exec, source and destination). Missing fields in legacy JSON default to unknown signatures and no detached wires; frozen state is derived from confirmed signatures and current definitions.
- **Scenario sheets persistence.** Graphs are organized into scenario sheets (`data/sheets.json` with metadata, and each sheet's graph in `data/sheets/<sheet-id>.json`). Legacy `data/graph.json` is automatically migrated on startup into a default "Main" sheet and renamed to `graph.json.migrated`. Deleted sheets move to `data/sheets/trash/<id>-<timestamp>.json`. Writes are pretty-printed, atomic (tmp + rename), debounced ~1 s and done on SIGTERM. A corrupt sheet or meta file fails the start-up (never overwritten silently).
- Plugins are `data/plugins/*.wasm`; their files live in `data/plugin-data/<name>/`; settings and state in `data/plugin-config/<name>.json` (all outside git; configs contain secrets).
- **Environment overrides for plugin settings.** `TICKNODE_PLUGIN_<PLUGIN>_<KEY>` (the plugin name and the setting key uppercased, every non-alphanumeric character becomes `_`; for example `TICKNODE_PLUGIN_HOME_ASSISTANT_TOKEN`) supplies a setting value when the stored config has none (a missing key or an empty string); stored values win. The text is parsed by the setting kind (number, bool `true/false/1/0/yes/no/on/off`, otherwise a string) and a value that does not fit is ignored with a warning. Secrets supplied this way still never reach the editor, and the panel treats them as set; the override is not written into the config file. This is how the Home Assistant add-on passes `SUPERVISOR_TOKEN` (`ticknode-server/src/plugins.rs`, `stored_with_env`).
- `data/plugin-config/<name>.json` is `{"enabled": bool, "settings": {key: DataValue}}`, written atomically with file mode 0600 (directory 0700). A plugin without a file is enabled with default settings. A corrupt file gives the `Error` state and is not overwritten silently (only by explicitly saving settings or enabling the plugin).

### Editor protocol
- **Node errors.** `Init.node_errors` snapshots runtime `NodeError { node, message: UiMessage, age_ms, count }`; appended `NodeErrors { set, cleared }` sends deduplicated changes every telemetry interval. `HostState::error` preserves English logs and records structured errors (nil owners are excluded). Successful execution, a pulse, a task result or a valid emission clears an error only if no error occurred for that node during the same tick; node edits, removal and plugin transitions clear it too. Errors are not persisted.
- `SetFrame(Frame)` / `RemoveFrame(FrameId)` → `FrameSet` / `FrameRemoved` manage comment boxes (layout only, up to 500 frames). Both are undoable and allowed in Batch; identical replacements or unknown removals emit nothing. `Init.frames` carries all frames. Snippet paste re-keys frames and includes them in the same history entry.
- `ResizeNode { id, size: Option<NodeSize> }` → `NodeResized` is an undoable layout edit, allowed in Batch; `None` restores automatic size. Finite sizes are clamped to shared bounds; no-ops emit nothing. Sizes live beside positions in the actor, persist in `NodeModel.size`, and survive snippets and history without recreating engine nodes. Settings paste preserves size.
- `ConfirmPins(NodeId)` accepts a frozen node's current signature and emits `NodeUpdated`; `RemoveDetached(DetachedConnection)` emits `DetachedRemoved`. Both are undoable and allowed in Batch; no-ops produce no events/history. `Init.detached_connections`, `Detached`/`DetachedRemoved` and `NodeInstance.frozen` carry this state. Undo/Redo restores signatures and detached wires without recreating untouched nodes; plugin revival emits `Detached` for invalid wires.
- Wire routes are layout only: `SetWireRoute(WireRoute)` → `WireRouted`; `Init.wire_routes` carries all routes. The actor validates at most 32 finite points on an existing connection, persists them in `GraphModel.wire_routes`, prunes disconnected routes, and includes point edits in shared Undo/Redo and Batch. The engine ignores routes.
- `ClientMessage::AddNodeConnected { type_name, position, from: ConnectionEnd { node, pin }, pin }` creates a default node and connects it to the existing pin as one undoable edit (also allowed in Batch). The actor derives direction and exec/data kind from effective pins, reuses the connection event paths (including `DataDisconnected` when replacing a source), and rolls back the new node on rejection without events or history. Success replies with `Created` after broadcasting.
- `ClientMessage::AddNodeWith { type_name, position, properties }` creates a node initialized with the given properties and position as one undoable edit (allowed in Batch). Keys starting with `in:*` or `split:*` are rejected with `error-invalid-property`; an unknown type returns `error-unknown-node-type`. Success broadcasts `NodeAdded` and replies `Created` to the initiator.
- `ClientMessage::PasteSettings { id, type_name, properties }` replaces all stored properties of an available node of the same type, including `in:*` and `split:*`. The actor validates the destination and reconciles a graph snapshot through the same event builder as Undo/Redo, preserving IDs and positions and dropping invalid connections. Recreated nodes with the same ID emit `NodeUpdated`; unchanged connections emit no events, preserving editor selection. It is one undoable edit, allowed inside Batch; identical settings produce no events or history entry. Undo restores the old settings and connections.
- Undo/Redo history belongs to the server actor and is scoped per scenario sheet (up to 100 snapshots, including positions). `ClientMessage::Undo` / `Redo` operate on the active sheet without affecting other sheets: only removed or changed nodes are recreated, preserving IDs and runtime state of untouched nodes; variables and the execution queue are not reset. `Init.history` and `ServerMessage::History(HistoryState { can_undo, can_redo })` report availability after command events. Successful edits clear redo; failed or no-op commands leave history untouched. Enabling/disabling a plugin clears all sheet stacks.
- `ClientMessage::Batch(Vec<ClientMessage>)` groups multiple graph edits into one history entry (multi-node moves/deletes and Match inputs/cases). Commands apply in order; partial successes remain and the first error is returned. Nested Batch, Undo, Redo, TriggerNode, SetPluginEnabled and ConfigurePlugin inside Batch are rejected and skipped. Protocol variants and Init fields must only be appended because postcard is positional.
- **Scenario sheets protocol and routing.** Clients manage sheets via `CreateSheet`, `UpdateSheet`, `DeleteSheet`, `MoveSheet`, `DuplicateSheet`, and `OpenSheet(Option<SheetId>)`. Each WebSocket session tracks its `open_sheet` (defaulting to the first sheet or selected sheet upon `OpenSheet`). Commands from a session mutate its open sheet; cross-sheet connections are rejected with `error-cross-sheet`. Broadcast events are tagged `(Option<SheetId>, Bytes)`: global events (`None`) reach all sessions, while sheet-scoped events only reach sessions viewing that sheet. Periodic telemetry splits `Executed`, `Timers`, and `NodeErrors` per sheet; sheet summaries (`Sheets`) debounce across 2 seconds on sheet changes.
- **Delay telemetry.** Host delay tasks retain start/due ticks. `TickEngine::delay_timers()` returns one `NodeTimer { node, total_ms, remaining_ms, count }` per owner; the first started task (start tick, then task ID) supplies progress, while count includes all active delays. Durations use the current tick length. Cancelled/delivered tasks disappear. `Init.timers` and appended `ServerMessage::Timers` carry the full list; telemetry samples it every interval and broadcasts only when `(node, first task ID, count)` changes, never for remaining time alone.
- After connecting, the server sends `ServerMessage::Init` (definitions, types, plugins, open sheet graph, sheet summaries, and active `open_sheet`), then change events (`NodeAdded`, `NodeUpdated`, `DataConnected`, …) and telemetry (`Executed`, `Log` from Console/Debug) at a fixed rate independent of the tick (`actor/telemetry.rs`: every 100 ms, traces merged per node with the union of fired pins, at most 1000 log lines per interval plus one "dropped" line). The server is the source of truth: the editor sends `ClientMessage`s and applies changes only from server events (events may be duplicated, so handle them idempotently). Errors go only to the client that caused them (`Error(UiMessage)`).
- `Created(ids)` goes only to the initiator of `AddNode` / `AddNodeConnected` / `Paste`, after the matching `NodeAdded`s: the actor replies after broadcasting, and `ws.rs` (`select!` with `biased`) delivers events first.
- Plugins: `Init` contains `plugins: Vec<PluginInfo>`; a state or settings change is announced to every editor with `PluginUpdated(PluginInfo)`, a change in the set of nodes/types (enable, disable) with `Catalog { definitions, types }` plus `NodeUpdated` for converted nodes (and `Detached` for pin connections that became invalid). The client sends `SetPluginEnabled { name, enabled }` and `ConfigurePlugin { name, values: [(key, SettingUpdate)] }`, where `SettingUpdate` is `Set(value)` / `Keep` / `Clear`. **Secrets (`SettingKind::Secret`) never reach the editor**: `PluginInfo.values` holds only `Secret { is_set }` for them. `NodeInstance.unavailable: Option<UiMessage>` explains a stub node; `PluginInfo.error` / `settings_error` are `UiMessage`s too.

### Execution model (`TickEngine::tick`)
- **Work budget and engine settings.** `ServerSettings { tick_ms: u32, tick_budget: u32 }` (default 100 ms / 0 = unlimited) is stored in `data/settings.json`, falling back to `TICKNODE_TICK_MS` and `TICKNODE_TICK_BUDGET` when absent. `TickEngine::budget: TickBudget { limit: Option<u32> }` owns the per-tick scheduling policy. `None` is unlimited. Ticks can be as short as 1 ms (clamped to 1..=10,000 ms; budget clamped to 0..=1,000,000). A live change takes effect immediately and updates `engine.host_state.tick_duration` and `engine.budget`. Protocol: `Init.server_settings`, `ClientMessage::SetServerSettings(ServerSettings)` (allowed on the home page, not undoable, not in batch), `ServerMessage::ServerSettingsChanged(ServerSettings)` broadcast to all sessions. `NodeDefinition.cost` is relative work, not milliseconds: cost ≈ relative work; native logic 1. A definition may derive its cost from node properties. Defaults: native nodes 1, `list/add` and `list/remove` 5; math/string/delay plugin nodes 2; http-weather 100; Home Assistant action 50, cache/entity/trigger/condition nodes 2. Plugin authors set `.cost(n)` on the SDK's definition (default 1); all components must be rebuilt after the WIT change.
- Each tick starts with zero spent work. Task deliveries, valid applied plugin emissions, and every event-source poll (even without a pulse) spend the node's cost before the execution queue. `Node::polls()` identifies event sources; ordinary nodes are not polled. Source activation execution costs separately. An activation is deferred when `spent > 0` and `spent + cost > limit`; with no work spent, even an oversized activation runs. Deferred activations retain FIFO order ahead of new next-tick hops. Pure nodes pulled during an activation also cost work, without interrupting it. `last_tick: TickStats { spent, deferred }` reports saturated work units and the number of postponed activations; it is reset every tick, including idle ticks. Unlimited scheduling preserves the existing execution order. This policy type is the extension point for future load adaptation and graph shares; neither is implemented yet.
- **Per-tick cost follows activity, not graph size.** `ConnectionIndex` (`engine/connections_index.rs`) maps exec successors and incoming data connections; effective definitions are cached as `Arc<NodeDefinition>` (`definition_arc`, validated by `Node::definition_revision`); `sources` (`Node::polls`) and `live_nodes` (`Node::needs_live`) are the only nodes an idle tick visits; `executed_index` finds a node's trace. All are maintained in `add_node`, `remove_node`, `set_node_property`, `set_pin_split` and type/plugin registration: never insert into `nodes` directly. `tests/definitions.rs` checks the cache and the sets against fresh values after every kind of edit.
- **Exec flow is push**: `NodeOutput::Execution` queues the next nodes for the **next** tick, so exec loops are safe.
- **Data flow is pull**: before `execute` the engine recursively pulls input values and applies connection conversions from declared source/destination types. Failed conversions supply no value; required inputs block execution and log once until values recover, while optional inputs see no value. Pure nodes (`is_pure()`) are cached in `pure_cache`, cleared every tick and after each execution that changed data/variables; results of active nodes live in `data_cache`.
- **Variables and scopes.** Variables are runtime data shared by the graph and the user (`VariableStore`, `ticknode-core/src/variables.rs`). Three scopes: `Sheet` (scoped to a `SheetId`, lost on restart), `Global` (all sheets, transient), and `Persistent` (saved to `data/variables.json` with mode 0600, debounced save). Global and Persistent share one namespace; a sheet variable shadows a global variable of the same name for nodes on that sheet. Typed with any `DataType` (validated via `TypeRegistry::compatible` and `convertible`). Limits: max 10,000 variables in total, max 64 KiB postcard serialized value. Nodes on a sheet resolve via `VariableLookup` (`Auto` resolves sheet first then global/persistent, `Sheet`, `Global`). Nodes: `variable/get` (pure: Value 0, Exists 1), `variable/set` (In 0, Out 1, Failed 2, Value 3 required), `variable/create` (In 0, Created 1, Exists 2, Initial 3 optional), `variable/delete` (In 0, Out 1), `variable/changed` (event source: Changed 0, Value 1). `NodeContext` provides read access (`ctx.variable`); writes go via `NodeOutput::Variable(VariableCommand)` applied immediately after node outputs. Plugins have no access to variables. Protocol: `Init.variables` carries global and persistent variables plus the open sheet's variables; `ServerMessage::VariablesChanged { set, removed }` is broadcast from the telemetry flush, split by sheet; `ClientMessage::CreateVariable`, `SetVariable`, `DeleteVariable` mutate variables (not undoable, not allowed in batch).
- Asynchronous tasks (delays in ticks, HTTP in tokio `spawn_blocking`) live in `HostState::active_tasks`. At the start of a tick finished tasks are removed and delivered to their owner node via `Node::on_task` (outputs are handled like in `execute`); then event sources are polled, then the queue runs. `remove_node` cancels the node's tasks.
- `HostState::logs` collects node messages for the tick (plugin errors included), `TickEngine::executed` — the nodes that ran (the server broadcasts both).

### WASM plugins (`wit/plugin.wit`, `plugin.rs`)
- `ticknode_shared::PLUGIN_API` fingerprints WIT text without comments/whitespace and the `DataValue` serde layout snapshot. Accept layout changes with `UPDATE_PLUGIN_VALUE_FORMAT=1 cargo test -p ticknode-shared plugin_value_format`; rebuild all plugins whenever the fingerprint changes. The SDK embeds it in a custom section that the host checks before instantiation.
- A plugin is a component (`cdylib`, `wasm32-wasip2`). It exports `manifest`, `definitions`, `types` (plugin-defined types, read together with `definitions`), `translations` (Fluent resources, see *Translations*), `configure`, `plugin-tick`, `create-node` and the `node` resource (`definition`, `properties`, `set-property`, `execute`, `poll`). Every graph node is a separate resource, so state lives in the node's fields. It imports `host`: `log`, `delay`, `start-http`, `cancel-task`, `ws-connect`/`ws-send`/`ws-close`, the tick. The host calls `poll` only for nodes with `polls: true` in their definition (SDK: `PluginNode::polls`).
- WIT has no recursive types: `DataValue` is passed as postcard bytes (`type value = list<u8>`), `DataType` as `{base, list-depth}` (`base` is a variant; a named type is `named(string)`). Both sides encode through `ticknode-shared`.
- Asynchronous work uses host tasks (`HostState::start_delay`/`start_http`): the plugin gets a `task-id`, the result arrives later as `trigger::task` (`Node::on_task` in the core). A task belongs to its node: it is cancelled when the node is removed, and a node cannot cancel another node's task.
- Capabilities: `Http` (domains checked by `start-http`; the host does not follow redirects — the node receives the 3xx), `WebSocket { allowed_hosts }` (hosts checked by `ws-connect` with the same `domain_allowed` matching, `ws://`/`wss://` only), `Storage` (WASI preopen of the plugin's directory as `.` — the plugin uses `std::fs`). No other WASI resources (network, env, args); WASI clocks work (`std::time::Instant`). The server grants what the manifest requests.
- **Plugin-owned WebSockets and `plugin-tick`** (`ws.rs`, `plugin.rs`). `host::ws-connect/ws-send/ws-close` work from any plugin call (`configure`, `plugin-tick`, `execute`, `poll`); the connection belongs to the plugin, not a node (`WsHub` lives in the instance's `PluginState`, so it dies on disable, on a trap and when the engine drops — after a trap `configure` runs again and the plugin reconnects; old ws-ids are void). Connections are tokio tasks on `HostState::runtime`: max 4 per plugin, max message 16 MiB, text frames only (binary frames are ignored), ping/pong by tungstenite (rustls + webpki roots for `wss`). `ws-connect` returns at once; `opened`/`message`/`closed` (a failed connect is `closed`) are drained by the engine and handed over in the export `plugin-tick(events) -> list<emission>`, at most 1000 events per tick per plugin (the rest stays queued). `TickEngine::tick` calls `plugin-tick` for every enabled plugin each tick, after finished tasks and before event sources are polled (`tick_plugins`); a trap discards the instance and pauses `plugin-tick` for 50 ticks. An `emission { node, outputs }` is applied like an execution of that node (`apply_outputs`: exec outputs queue downstream nodes for the next tick, data goes to `data_cache`, the trace is recorded). The host drops (English error log) emissions for unknown nodes, nodes of another plugin or stubs, pins that are not outputs of the right kind, and values failing `check_output_type`. Plugin-level logs carry the nil `NodeId`.
- **Node ids.** `create-node(type-name, node-id)` passes the graph `NodeId` as `(hi, lo)` halves of its UUID (WIT has no 128-bit integer); the SDK gives `Plugin::create(type, NodeId)` and `Emission { node: NodeId, outputs }`. A node recreated after a trap gets the same id; a removed node's resource is dropped (`Drop`). SDK: `host::ws_connect/ws_send/ws_close`, `WsEvent`, `Plugin::tick(events) -> Vec<Emission>` (default empty).
- One `Store` per plugin; each call is limited by fuel (`FUEL_PER_CALL`) and memory. On a trap the instance is recreated (its generation changes, so stale resources are never used), nodes are recreated lazily from `properties` (field state is lost) and the offending node stops until a property changes. The full backtrace goes to the server log, the editor console gets a short reason.
- **Synchronous wasmtime-wasi must not be called from a tokio task** (`in_tokio` → `Handle::block_on` panics). That is why the server runs the engine on its own OS thread and the plugin tests are plain `#[test]`s; the tokio runtime for HTTP is passed via `HostState::runtime`.
- `NodeDefinition::help` is the detailed explanation (the "info" tooltip in the palette and inspector); `description` is one line for the palette. A core test requires `help` for every built-in node.
- The category is the English string `NodeDefinition::category` (`Events`, `Control Flow`, `Time`, `Data`, `Math`, `Logic`, `String`, `Lists`, `Objects`, `Network`, `Debug`, `Actions`, `Test`). Order, colour and icon are in `ticknode-editor/src/categories.rs`; unknown plugin categories are shown as-is.
- A plugin cannot take over a node type that is already registered (built-in or from another plugin).
- **Plugin settings.** The schema is `PluginManifest.settings: Vec<SettingDefinition { key, title, description, kind: SettingKind (Text/Number/Bool/Secret/Url/Select), required, default }>` (builders `SettingDefinition::text/secret/select(..).required().default_value(..)`, `PluginManifest::new(..).setting(..)`). The user sets values in the Plugins panel; the host passes them through the WIT export `configure(settings: list<property>) -> result<_, ui-error>` (`ui-error` = `{key, args, fallback}`, SDK `UiError`, a `UiMessage`; the host drops a key outside the plugin's `<plugin slug>-` namespace) (missing values are replaced by `default`, an empty string means unset, see `effective_settings`). The host calls `configure` after enabling, on every settings change and **after an instance is recreated following a crash, before nodes are recreated** (`Runtime::instantiate`). An `Err` does not disable the plugin: it stays loaded and the error is shown in the panel (`PluginInfo.settings_error`). SDK: `Plugin::configure(&[(String, DataValue)]) -> Result<(), UiError>` (default `Ok`; `String`/`&str` convert to a fallback-only error, `UiError::new("my-plugin-error-x", "English text").arg("name", value)` has a key), helpers `setting_str/number/bool`; there is one instance per plugin, so keep settings in a `thread_local!`.
- **Resource collections.** `PluginManifest.resources: Vec<ResourceCollection { id, title, icon, source, actions: Vec<ResourceAction { title, type_name, property, requires_source }> }}` (builders `ResourceCollection::new(id, title, source).icon("mdi:..").action(ResourceAction::new(title, type_name, property).requires_source(src))`, `PluginManifest::resource(..)`). Exposed in `PluginInfo.resources` for the editor. Host validation at `add_plugin` drops (with an English warning log naming the plugin) collections with an empty/duplicate id or empty source, actions whose `type_name` is not among the plugin's node types or whose `property` is empty, and collections left without actions.
- **Enable/disable at runtime.** `TickEngine::add_plugin` only compiles the plugin and reads its manifest; `enable_plugin(name, settings)` registers its node types (`NodeRegistry::register_owned`) and data types (`TypeRegistry`, owners in `type_owners`), calls `configure` and turns its stubs into real nodes (invalid pin connections are detached and returned in `PluginChange.detached`; other removals remain in `PluginChange.removed`); `disable_plugin(name)` replaces the plugin's nodes (including Make/Break of its structs) with stubs, removes its types from the registries and drops the instance. Disabling is refused when another enabled plugin uses its types (in node pins or type fields). `load_plugin` = `add_plugin` + `enable_plugin` with default settings (for tests).
- **Stub nodes (`StubNode`)** keep `type_name`, all properties (including `in:*`) and the last known definition, so connections stay and `export_graph` is unchanged. A stub does not run (it logs "plugin <name> unavailable"); `set_node_property`/`set_input_value` return `EngineError::PluginUnavailable`. **An unknown type in `load_graph`/`import_snippet` also becomes a stub** (pins are restored from the graph's connections, a data pin's type from the other end or `Any`), so a graph with a node of an unknown plugin never loses it on save. When the type appears in the registry, the stub comes back to life.
