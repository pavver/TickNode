# AGENTS.md

Guidance for coding agents (Claude Code, Gemini / Antigravity, Codex, …) working in this repository. `CLAUDE.md` and `GEMINI.md` only import this file.

TickNode is a node-based visual programming system for automation. The goal is a Home Assistant add-on that replaces HA's built-in automations, while TickNode also runs standalone. Rust 2024 workspace. The concepts are described in `README.md` and `ARCHITECTURE.md`.

- The engine runs on the server (`ticknode-server`); the browser is only an editor (`ticknode-editor`, **Leptos** CSR). Plugins are WASM components (**wasmtime + WIT**, `wit/plugin.wit`). The editor↔server protocol is postcard; the types are shared through `ticknode-shared`. The graph is stored as JSON.
- **Integrations (Home Assistant included) are separate plugins, never part of the core or the server.** All third-party nodes run as WASM plugins with limited capabilities.

## Language rules

- Talk to the user in **Ukrainian**.
- Documentation (`*.md`) and code comments are in **English**.
- **Editor UI text** is localized with Mozilla Fluent (`en`, `uk`); never hard-code UI strings (see *Editor → Internationalization*).
- **Errors the user sees in the UI** (an answer to their action, a plugin settings error under the form, validation) must be translatable: send a message key with arguments plus an English fallback, not a ready-made sentence.
- **Logs are always English and are never translated**: the server log (`tracing`), node and plugin messages (`host::log`, `ServerMessage::Log`) and the editor console. This is deliberate: when a user reports a problem from any locale, their logs can be read without translation. Plugin authors must log in English.

## Commands

```bash
cargo build
cargo test -p ticknode-core -p ticknode-shared -p ticknode-server
cargo test -p ticknode-core --test plugins delay_queue -- --nocapture   # a single test

# Plugins are wasm32-wasip2 components. The integration tests (ticknode-core/tests/plugins.rs) load
# target/wasm32-wasip2/debug/*.wasm and are SKIPPED when the files are missing (TICKNODE_REQUIRE_PLUGINS=1 makes them fail)
cargo build --target wasm32-wasip2 -p delay-plugin -p string-plugin -p math-plugin -p http-weather-plugin -p test-plugin
# The server uses release builds copied to data/plugins/
cargo build --release --target wasm32-wasip2 -p math-plugin && cp target/wasm32-wasip2/release/math_plugin.wasm data/plugins/

# Server (env: TICKNODE_BIND=0.0.0.0:8099, TICKNODE_DATA_DIR=data, TICKNODE_WEB_DIR=ticknode-editor/dist, TICKNODE_TICK_MS=100, RUST_LOG)
cargo run -p ticknode-server

# Editor (Leptos CSR, trunk). Not in default-members: `cargo build` at the root does not build it
cd ticknode-editor && trunk build            # → dist/, served by the server
cd ticknode-editor && trunk serve            # dev on :8080, /ws is proxied to 127.0.0.1:8099
cd ticknode-editor && trunk build --release  # needs wasm-opt (trunk downloads it)
cargo test -p ticknode-editor --target x86_64-unknown-linux-gnu   # geometry and i18n tests (no browser)
```

- The `wasm-bindgen` version in `ticknode-editor/Cargo.toml` must match the wasm-bindgen-cli used by trunk.
- In the dev profile dependencies are built with `opt-level = 2`: unoptimized Cranelift compiles plugins tens of times slower.
- Never run the server against the real `data/` directory for experiments: it rewrites `data/graph.json`. Use a copy (`TICKNODE_DATA_DIR`).
- When the graph format or the protocol changes, update the types in `ticknode-shared` (shared by the server and the editor).

## Architecture

### Crates
- `ticknode-shared` — every serialized type: `DataValue`/`DataType`/`NumberValue`, plugin-defined types (`types.rs`: `TypeDefinition`, `TypeRegistry`), `NodeDefinition`/`PinDefinition`, `NodeOutput`, `Capability`/`PluginManifest` and plugin settings (`plugin.rs`), the graph model (`GraphModel`, `NodeModel`, `NodeInstance`, `ConnectionModel`, `Position`) and the editor protocol (`ClientMessage`, `ServerMessage`).
- `ticknode-core` — the engine: `lib.rs` (`Node` trait, `NodeRegistry`, `TickEngine`, built-in nodes), `host.rs` (`HostState`: tasks, HTTP, logs), `plugin.rs` (wasmtime plugin host, `WasmNode`), `custom_types.rs` (named types, Make/Break nodes), `stub.rs` (stub nodes).
- `ticknode-server` — axum: `/ws` (WebSocket, postcard) plus the editor's static files. `actor.rs` runs the engine on its own OS thread (ticks and commands sequentially, no locks); `storage.rs` — `graph.json`; `plugins.rs` — discovery of `data/plugins/*.wasm`, plugin state and `data/plugin-config/`; `ws.rs` — an editor session.
- `ticknode-editor` — the editor: `state.rs` (`Editor`, a `Copy` set of signals, `apply(ServerMessage)`), `i18n.rs` (Fluent, `t!`), `connection.rs` (WebSocket and reconnects), `canvas.rs` (camera, dragging, wires), `panels.rs` (palette, inspector, console), `plugins_panel.rs` (plugin state, toggle, permissions, settings form), `inline.rs` (properties and input values on the node), `match_editor.rs` (Match inputs and cases on the node), `ui.rs` (design-system components), `geometry.rs`.
- `ticknode-plugin-sdk` — the plugin SDK (wit-bindgen): `Plugin` (with `types()` and `configure()`) and `PluginNode` traits, `host::*`, `export_plugin!`, `StructValue` (builder for tagged values), `Inputs::field*` / `field*()` (reading fields). `*-plugin` are plugins; `test-plugin` exists only for host tests (crashes, fuel, storage, settings).

### Nodes and the graph
- A node is recreated from `type_name` + `properties()`; this is the only persistence/copy mechanism (`export_graph`, `load_graph`, `export_snippet`, `import_snippet`). Every configurable node implements `set_property` and `properties()` symmetrically.
- `NodeRegistry::register(creator)` takes the definition from an instance with default properties; definitions are not described separately.
- Pins may depend on properties (`math/expression` derives inputs from the formula's variables; `list/*`, `object/*` take the type from `element_type`/`field_type`). `set_node_property` removes connections that became invalid and returns them in `RemovedConnections`.
- A data input has one source: `connect_data` replaces the previous connection. `connect_exec` validates pins too.
- An unconnected data input (number/string/bool/any, enum) can get a value right on the node: `ClientMessage::SetInputValue`, `TickEngine::set_input_value`. It is stored among the properties as `in:<pin id>` (`input_value_property`) but is not passed to the node: `pull_inputs` substitutes it while nothing is connected. Values that no longer fit after a pin change are removed in `set_node_property`. Works for plugins too.
- **Plugin-defined data types.** `DataType::Named("ha.state")` refers to a `TypeDefinition` (`title`, `color` `#rrggbb`, `TypeKind::Struct { fields: FieldDefinition { name, title, description, data_type, optional } }` | `TypeKind::Enum { values }`). The name contains a dot (`is_type_name`) and is written as-is in text (`parse_data_type`/`data_type_name`, `*_type` properties, Match inputs). A struct value is `DataValue::Object` with `type_name: Some(..)` (`get_type()` → `Named`; `#[serde(default)]` without `skip_serializing_if`, since postcard is not self-describing); an enum value is a `DataValue::String` from the list (validated by `text::parse_value_in` / `input_value_fits`). The registry is `TickEngine::types` (`TypeRegistry`); a plugin adds its types atomically, and a name clash or an unknown type in a field or pin fails the plugin load. Pin compatibility goes only through `TypeRegistry::compatible` (the free `types_compatible` knows only `Any`): `Named(a)→Named(a)`, `Named↔Any`, `Named(struct)→Object`, `Named(enum)→String`; never `Object→Named` or `String→Named`. For every struct the engine adds pure nodes `type/make/<name>` (fields → value; pin 0 is the output, fields are 1..=N) and `type/break/<name>` (pin 0 is the input, fields 1..=N; a missing optional field has no value), category `Data` (`custom_types.rs`). **Add new struct fields only at the end**: pins are positional. In Match a struct behaves like an Object (`condition::ops_in`), an enum offers `=`/`≠`/`has value` with a drop-down of values. A plugin node may not put an object with a foreign or missing tag on a `Named` output: the host drops the value and logs an error.
- **Required inputs.** `PinDefinition::required` (`serde(default)`; WIT `pin.required`; SDK `data_in(..).required()`). An input is set when a source is connected or, for text types and enums, a value is set on the node (`in:<pin>`); struct/list inputs need a connection. A node with an unset required input does not run (a pure node yields no value, an active node's `execute` is not called) and logs an error once until the state changes. A connected source without a value is skipped silently. In Make the required inputs are the non-optional fields. The editor highlights such a pin and node as Error (`Editor::required_missing`).
- `match` is a decision combinator. Properties: `inputs`, a list of `"<pin>:<name>:<type>"` (type `any` = "auto"), and `cases`, a list of `"<pin>: a > 10 and b != \"on\""` (parsing, evaluation and display live in `ticknode_shared::condition`; `and` binds tighter than `or`). Operators depend on the left input's type (`ops_for`: comparisons for numbers/time/duration, `contains`/`starts_with`/`len_*` for strings and lists, `has_field` for objects, unary `is_true`, `is_empty`, `has_value`, …); the right side is a constant or another input, and a constant is coerced to the input's type (`text::coerce_to`: `"07:30"` → time). A graph without `inputs` is the old format: inputs are derived from the names in conditions (Any, pins 1.. alphabetically), but only during `create_node`; after `Node::restored` the inputs are explicit, both in a new and in a loaded node. Each case is an exec output with a stable pin number; Else is pin 0. There is no separate Branch node.
- The text form of values (fields on nodes, conditions) is `ticknode_shared::text`: `parse_value(text, &DataType)` / `format_value`; time `HH:MM[:SS]`, date-time `YYYY-MM-DD HH:MM`, duration `90` / `1h 30m` / `500ms`, color `#rrggbb[aa]`.
- Node positions belong to the server, not the engine; they are written into `NodeModel.position` only when saving.

### Persistence
- `data/graph.json` is pretty-printed JSON with a stable order (nodes/connections sorted, object fields in a `BTreeMap`) so that it diffs well in git. Writes are atomic (tmp + rename), debounced ~1 s and done on SIGTERM. A corrupt file fails the start-up (it is never overwritten with an empty graph).
- Plugins are `data/plugins/*.wasm`; their files live in `data/plugin-data/<name>/`; settings and state in `data/plugin-config/<name>.json` (all outside git; configs contain secrets).
- `data/plugin-config/<name>.json` is `{"enabled": bool, "settings": {key: DataValue}}`, written atomically with file mode 0600 (directory 0700). A plugin without a file is enabled with default settings. A corrupt file gives the `Error` state and is not overwritten silently (only by explicitly saving settings or enabling the plugin).

### Editor protocol
- After connecting, the server sends `ServerMessage::Init` (definitions, types, plugins and the whole graph), then change events to every editor (`NodeAdded`, `NodeUpdated`, `DataConnected`, …) and telemetry (`Executed` every tick, `Log` from Console/Debug). The server is the source of truth: the editor sends `ClientMessage`s and applies changes only from server events (events may be duplicated, so handle them idempotently). Errors go only to the client that caused them (`Error`).
- `Created(ids)` goes only to the initiator of `AddNode` / `Paste`, after the matching `NodeAdded`s: the actor replies after broadcasting, and `ws.rs` (`select!` with `biased`) delivers events first.
- Plugins: `Init` contains `plugins: Vec<PluginInfo>`; a state or settings change is announced to every editor with `PluginUpdated(PluginInfo)`, a change in the set of nodes/types (enable, disable) with `Catalog { definitions, types }` plus `NodeUpdated` for converted nodes (and `*Disconnected` for connections that became invalid). The client sends `SetPluginEnabled { name, enabled }` and `ConfigurePlugin { name, values: [(key, SettingUpdate)] }`, where `SettingUpdate` is `Set(value)` / `Keep` / `Clear`. **Secrets (`SettingKind::Secret`) never reach the editor**: `PluginInfo.values` holds only `Secret { is_set }` for them. `NodeInstance.unavailable` explains a stub node.

### Editor
- The design is the Operator UI design system (reference Kotlin components: `/home/pavver/rust/notifiApp/NotifiApp/design_system/`): tokens in `style.css` (`:root` / `[data-theme=light]`), unit `--du: 4px`, square corners, control states Idle/Selected/Pending/Success/Error (`ui::ControlState`).
- Wires are built from computed pin positions (`geometry.rs`), not measured in the DOM: the constants `DU`, `NODE_WIDTH` / `MATCH_WIDTH` (width — `NodeLayout::width`) and the header/row heights must match the CSS of `.node-header`, `.node-props`, `.pins`, `.pin`. `NodeLayout` gives pin positions and the node size: simple properties (text-typed, except `in:*`) are rows between the header and the pins; in Match, after In, the input rows and the "+ input" row come the case blocks (`case_rows`), each case's exec output sits in its block header, Else in the last row.
- All settings live on the node itself (properties, `*_type` drop-downs, input values, Match conditions, ▶ "run" in the header); the inspector shows the description, the last execution and actions. Controls on a node must not let `pointerdown` reach the canvas (`stop_on_controls`), or a drag starts.
- A dynamic `class=move || …` overwrites the whole `className`, so do not combine it with `class:x=…` on the same element: build the class as one string.
- Fields that may lose focus after being removed from the DOM read signals via `try_*`. Node signals (`ClientNode`) are disposed lazily (`dispose_later`), and `Init` updates existing nodes in place.
- In `view!`, an attribute expression containing `<` or `>` must be wrapped in `{…}`, or the macro takes it for the end of the tag.
- The editor never changes the graph locally: action → `ClientMessage`, state is updated only from `ServerMessage`s (exception: a node's position while it is dragged).
- Below 900 px the panels become overlays (`Editor::narrow`).
- The **Plugins** panel (toolbar button, `Editor::show_plugins`) takes the inspector's place. A plugin card: name, version/author, state chip (`ControlState`: Success — running, Idle — disabled, Error — error with text; a separate "settings error" chip), the enable switch (`Switch`, Pending until the server answers), permissions, a settings form generated from the schema and "Save" → `ConfigurePlugin`; a `configure` error is shown under the form. A secret field is a password input with a "set" placeholder and a "Clear" button; an empty field means `Keep`. A stub node (`NodeInstance.unavailable`) is dimmed, shows "plugin unavailable" and its properties and input values are read-only (CSS `.node.unavailable`).
- Canvas controls: the middle button pans (on touch — a finger on the background), left button on the background draws a selection box (left-to-right — "window", only fully enclosed nodes; right-to-left — "crossing"). Palette: click adds a node, dragging drops it under the cursor.
- Clipboard: `copy`/`cut`/`paste` events (work without HTTPS); a snippet is JSON `{"format":"ticknode/snippet@1","graph":GraphModel}` (`clipboard.rs`). Ctrl+V does not create nodes immediately: the snippet becomes `Editor::pending_paste` and follows the cursor (left button — `ClientMessage::Paste`, right button/Esc — cancel; the middle button pans). A `paste` right after a middle click is ignored: that is Linux's primary-selection paste. The server assigns new IDs and answers the initiator with `Created` to select the pasted nodes.
- The inspector shows a node's last execution from `NodeTrace` (inputs, outputs, fired exec pins, "N seconds ago"). The server sends traces in `Executed` every tick and the latest ones with their age in ms in `Init`; they live only in memory.
- Named types in the editor: `Editor::types`, `geometry::type_color` (the type's `color`, otherwise a hash of the name), `Editor::type_title`; an unconnected enum input is a drop-down (`InlineValue`).
- **Internationalization (`i18n.rs`, Mozilla Fluent).** Locales `en` and `uk`. Translations live in `ticknode-editor/locales/{en,uk}/ui.ftl` (UI, categories, data types, Match operators) and `nodes.ftl` (built-in nodes by `type_name` with `/` and `_` replaced by `-`: `node-<slug>-title`, `-description`, `-help`, `-pin-<name>`) and are embedded with `include_str!`. The active locale is `RwSignal<Locale>` in the Leptos context (`Editor::locale`), stored in `localStorage` (`ticknode.locale`; default — the browser language: `uk*` → `uk`, otherwise `en`). **Every new UI string goes through `t!("key")` / `t!("key", arg = val)` and must exist in both locales.** For built-in nodes use `i18n::node_title`, `node_description`, `node_help`, `node_pin_label`; plugin nodes and Make/Break nodes without a key show the server's text. The editor tests check `.ftl` syntax, identical key sets in both locales and that every `t!("...")` key exists.

### Execution model (`TickEngine::tick`)
- **Exec flow is push**: `NodeOutput::Execution` queues the next nodes for the **next** tick, so exec loops are safe.
- **Data flow is pull**: before `execute` the engine recursively pulls input values. Pure nodes (`is_pure()`) are cached in `pure_cache`, cleared every tick and after each execution that changed data/variables; results of active nodes live in `data_cache`.
- `NodeOutput::Variable` writes to the global `variables` (shared by the whole graph). Plugins have no access to variables — only through pins.
- Asynchronous tasks (delays in ticks, HTTP in tokio `spawn_blocking`) live in `HostState::active_tasks`. At the start of a tick finished tasks are removed and delivered to their owner node via `Node::on_task` (outputs are handled like in `execute`); then event sources are polled, then the queue runs. `remove_node` cancels the node's tasks.
- `HostState::logs` collects node messages for the tick (plugin errors included), `TickEngine::executed` — the nodes that ran (the server broadcasts both).

### WASM plugins (`wit/plugin.wit`, `plugin.rs`)
- A plugin is a component (`cdylib`, `wasm32-wasip2`). It exports `manifest`, `definitions`, `types` (plugin-defined types, read together with `definitions`), `configure`, `create-node` and the `node` resource (`definition`, `properties`, `set-property`, `execute`, `poll`). Every graph node is a separate resource, so state lives in the node's fields. It imports `host`: `log`, `delay`, `start-http`, `cancel-task`, the tick. The host calls `poll` only for nodes with `polls: true` in their definition (SDK: `PluginNode::polls`).
- WIT has no recursive types: `DataValue` is passed as postcard bytes (`type value = list<u8>`), `DataType` as `{base, list-depth}` (`base` is a variant; a named type is `named(string)`). Both sides encode through `ticknode-shared`.
- Asynchronous work uses host tasks (`HostState::start_delay`/`start_http`): the plugin gets a `task-id`, the result arrives later as `trigger::task` (`Node::on_task` in the core). A task belongs to its node: it is cancelled when the node is removed, and a node cannot cancel another node's task.
- Capabilities: `Http` (domains checked by `start-http`; the host does not follow redirects — the node receives the 3xx), `Storage` (WASI preopen of the plugin's directory as `.` — the plugin uses `std::fs`). No other WASI resources (network, env, args). The server grants what the manifest requests.
- One `Store` per plugin; each call is limited by fuel (`FUEL_PER_CALL`) and memory. On a trap the instance is recreated (its generation changes, so stale resources are never used), nodes are recreated lazily from `properties` (field state is lost) and the offending node stops until a property changes. The full backtrace goes to the server log, the editor console gets a short reason.
- **Synchronous wasmtime-wasi must not be called from a tokio task** (`in_tokio` → `Handle::block_on` panics). That is why the server runs the engine on its own OS thread and the plugin tests are plain `#[test]`s; the tokio runtime for HTTP is passed via `HostState::runtime`.
- `NodeDefinition::help` is the detailed explanation (the "info" tooltip in the palette and inspector); `description` is one line for the palette. A core test requires `help` for every built-in node.
- The category is the English string `NodeDefinition::category` (`Events`, `Control Flow`, `Time`, `Data`, `Math`, `Logic`, `String`, `Lists`, `Objects`, `Network`, `Debug`, `Actions`, `Test`). Order, colour and icon are in `ticknode-editor/src/categories.rs`; unknown plugin categories are shown as-is.
- A plugin cannot take over a node type that is already registered (built-in or from another plugin).
- **Plugin settings.** The schema is `PluginManifest.settings: Vec<SettingDefinition { key, title, description, kind: SettingKind (Text/Number/Bool/Secret/Url/Select), required, default }>` (builders `SettingDefinition::text/secret/select(..).required().default_value(..)`, `PluginManifest::new(..).setting(..)`). The user sets values in the Plugins panel; the host passes them through the WIT export `configure(settings: list<property>) -> result<_, string>` (missing values are replaced by `default`, an empty string means unset, see `effective_settings`). The host calls `configure` after enabling, on every settings change and **after an instance is recreated following a crash, before nodes are recreated** (`Runtime::instantiate`). An `Err` does not disable the plugin: it stays loaded and the error is shown in the panel (`PluginInfo.settings_error`). SDK: `Plugin::configure(&[(String, DataValue)]) -> Result<(), String>` (default `Ok`), helpers `setting_str/number/bool`; there is one instance per plugin, so keep settings in a `thread_local!`.
- **Enable/disable at runtime.** `TickEngine::add_plugin` only compiles the plugin and reads its manifest; `enable_plugin(name, settings)` registers its node types (`NodeRegistry::register_owned`) and data types (`TypeRegistry`, owners in `type_owners`), calls `configure` and turns its stubs into real nodes (invalid connections are removed and returned in `PluginChange.removed`); `disable_plugin(name)` replaces the plugin's nodes (including Make/Break of its structs) with stubs, removes its types from the registries and drops the instance. Disabling is refused when another enabled plugin uses its types (in node pins or type fields). `load_plugin` = `add_plugin` + `enable_plugin` with default settings (for tests).
- **Stub nodes (`StubNode`)** keep `type_name`, all properties (including `in:*`) and the last known definition, so connections stay and `export_graph` is unchanged. A stub does not run (it logs "plugin <name> unavailable"); `set_node_property`/`set_input_value` return `EngineError::PluginUnavailable`. **An unknown type in `load_graph`/`import_snippet` also becomes a stub** (pins are restored from the graph's connections, a data pin's type from the other end or `Any`), so a graph with a node of an unknown plugin never loses it on save. When the type appears in the registry, the stub comes back to life.
